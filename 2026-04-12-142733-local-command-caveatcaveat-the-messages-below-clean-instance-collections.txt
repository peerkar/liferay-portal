❯ why does creating empty expando shells succeed with navigation menus then?    

● Because the code paths are different:

  NavigationMenu goes through CustomFieldsUtil.toMap() which calls
  expandoBridge.addAttribute(name, type) for each custom field. addAttribute()
  internally calls getTable():

  // ExpandoBridgeImpl.addAttribute() → line 132
  ExpandoTable table = getTable();

  And getTable() creates the table if missing:

  // ExpandoBridgeImpl.getTable() → line 641
  ExpandoTable table =
  ExpandoTableLocalServiceUtil.fetchDefaultTable(_companyId, _className);
  if (table == null) {
      table = ExpandoTableLocalServiceUtil.addDefaultTable(_companyId,
  _className);
  }

  So by the time values are set, both the table and columns already exist.

  FileEntry staging import skips that entirely. The ServiceContext already has
  serialized expandoBridgeAttributes from the export data (set by
  PortletDataContextImpl.createServiceContext at line 1960). Then
  DLFileEntryLocalServiceImpl._addFileVersion calls
  ExpandoBridgeImpl.setAttributes(Map, boolean) which goes straight to
  ExpandoValueLocalServiceUtil.addValues() →
  _expandoTablePersistence.findByC_C_N() — no getTable(), no table creation,
  just a hard findByC_C_N that throws NoSuchTableException.

  So the difference is: addAttribute → creates table first. setAttributes →
  assumes table exists.

❯ Could we use the same approach with file entries?                             

● Not directly with CustomFieldsUtil.toMap(), because the data shapes are
  different:

  - NavigationMenu (headless API): has CustomField[] DTOs with name and
  attributeType → can call expandoBridge.addAttribute(name, type) to create both
   table and columns
  - FileEntry (staging import): has a serialized Map<String, Serializable> from
  the export zip → no attribute type info available to create columns

  But we could use the same underlying mechanism. The
  FileEntryStagedModelDataHandler.doImportStagedModel already creates the
  ServiceContext at line 400:

  ServiceContext serviceContext = portletDataContext.createServiceContext(
      fileEntry, DLFileEntry.class);

  We could get an ExpandoBridge and call addAttribute() for each expando entry
  before the file entry is added. The challenge is we'd need to infer the column
   type from the serialized value.

  Alternatively, the simplest version is just ensuring the ExpandoTable exists
  (the table is what's missing, not the columns — missing columns are already
  handled gracefully by addValues). That could be done in the
  FileEntryStagedModelDataHandler directly, or more generally wherever the
  ServiceContext's expandoBridgeAttributes get applied.

  What approach would you prefer?

❯ what do you recommend?                                                        

● I'd go with the fix in ExpandoBridgeImpl.setAttributes(Map, boolean) — the one
   I proposed earlier. Here's why:

  1. It's the right level of abstraction. The bug is that setAttributes assumes
  the table exists while addAttribute doesn't. Making them consistent by adding
  the same getTable() call fixes the asymmetry.
  2. It's general. Any staged model with expandos hitting a system without the
  table will benefit — not just FileEntry, not just AssetListEntry imports. You
  won't need to patch individual data handlers one by one.
  3. It's minimal. Four lines, using an existing method that's already called by
   addAttribute() in the same class.
  4. Missing columns are already handled. Once the table exists, addValues
  queries for columns by name, gets an empty list, and sets nothing — that's
  already the "empty shell" behavior without any further changes.
  5. The cost is negligible. getTable() calls fetchDefaultTable which hits the
  entity cache. It only runs during import
  (ExportImportThreadLocal.isImportInProcess()), so normal runtime is untouched.
